02

Six kinds of operation, kept apart

Key generation

Creating secret material from randomness. It is the only non-deterministic step: a CSPRNG draws 128–256 bits. Its quality bounds everything after it, because nothing downstream can add entropy.

Pipeline: entropy for the mnemonic. Property: unpredictable and uniform.

Key derivation

Computing new keys deterministically from existing secrets with a keyed pseudo-random function (HMAC-SHA512). It adds no entropy. It spreads one secret into many keys that look independent.

Pipeline: PBKDF2 seed stretching, BIP-32 child keys along the BIP-44 path.

Public-key cryptography

A one-way relation between a private and a public key (Q = kG) that also supports signatures: anyone can verify, only the holder of k can sign.

Pipeline: secp256k1 public key; ECDSA signatures on every transaction.

Hashing

Unkeyed map from arbitrary input to a fixed-size digest that behaves like a random function. Preimage, second-preimage and collision resistance, plus the avalanche effect.

Pipeline: Keccak-256 for the address. SHA-256 and SHA-512 inside the BIP-39 checksum, HMAC and PBKDF2.

Checksums

Redundancy that detects accidental errors (typos, swapped words). Not a security mechanism against an adversary: anyone can compute a valid checksum.

Pipeline: the last 4–8 bits of a BIP-39 phrase, the letter case of an EIP-55 address.

Encoding

A reversible change of representation with no secret and no loss: bits ↔ words, bytes ↔ hex, a mixed-case display. It provides no confidentiality.

Pipeline: the BIP-39 wordlist, hexadecimal addresses, EIP-55 capitalisation.

Generation vs derivation: generation answers "where does the secret come from?" (randomness). Derivation answers "how do I get more keys out of it?" (a deterministic function). A wallet does one generation and unlimited derivations. That is why backing up 12 words backs up every account the wallet will ever create.

Statistical properties, step by step

StageDistribution / entropyStatistical fact worth knowing
EntropyUniform on {0,1}ENT, ENT = 128 or 256All later uniformity is inherited from here. A biased RNG cannot be repaired downstream: a "uniform-looking" address from 32 bits of entropy is still brute-forceable.
Mnemonic204812 = 2132 word sequences, 2128 validA random 12-word sequence has a valid checksum with probability 2−4 = 1/16 (24 words: 2−8). The first 11 words are free. Given them, only 128 of the 2048 possible last words are valid.
SeedPseudo-random 512 bitsPBKDF2 adds ~11 bits of work (211 rounds) but no entropy. A wrong passphrase is undetectable: it gives a different, equally random-looking wallet.
BIP-32 child keys≈ uniform on [1, n−1]IL ≥ n happens with probability ≈ 3.7 × 10−39. Siblings look independent, but for normal (non-hardened) children kchild − kparent = IL is computable from the xpub. Leaking one child private key plus the xpub reveals the parent key, which is why the account levels are hardened.
Public keyUniform over the 2256-point group, not over 512-bit stringsX takes only about half the values below p, and Y is determined by X up to sign. 64 bytes carry about 256 bits of entropy. As in HW1, the structure is there by design.
Keccak-256 / address≈ uniform on {0,1}160Avalanche: one flipped input bit changes ≈ 128 ± 8 of the 256 output bits. 160-bit addresses give ~280 collision resistance (birthday bound) and 2160 for a second preimage.
EIP-55Letter count L ~ Binomial(40, 6/16), mean 15Each letter carries one check bit, so a random error passes with probability E[2−L] = (10/16 + 6/16 · ½)40 = (13/16)40 ≈ 0.0247%, the figure quoted in EIP-55. All-lowercase and all-uppercase input carry no check at all. By the same formula, about 2 · 0.0247% ≈ 0.05% of addresses have a correct EIP-55 form that is single-case, so validators cannot tell them from unchecked input.

Experiments: measure it

Monte Carlo estimates of the probabilities above, using the same code as the demo. Intervals are 95% Wilson score intervals. The experiments start when this section scrolls into view and take a few seconds. A 95% interval misses the true value 1 time in 20, so an occasional "outside" is expected. Press run again and it should move.

A · BIP-39 checksum: how often does a wrong phrase pass?

B · EIP-55: how often does a typo pass?

A random address gets one character replaced, typed in a random case, and is then validated as wallets do: mixed case must match the checksum, single-case input is accepted unchecked. A typo can get through in two ways. The first is luck: a checksum collision. The second is that the typed address ends up all-lowercase or all-uppercase, so there is nothing to check. That happens when the correct address is itself single-case (≈ 0.049% of addresses), or when the typo replaces its only uppercase or only lowercase letter. The second way adds about 0.05 percentage points, so the total is roughly three times the naive 0.0247%.

C · Keccak-256 avalanche

Changed output bits after flipping one input bit

Input: random 64-byte strings, the size of an uncompressed public key without prefix. Flip one random bit and compare the two digests.

For a random function the number of changed bits is Binomial(256, ½): mean 128, standard deviation 8. The observed histogram should match the curve. A visible shift or excess spread would be a statistical defect, which is exactly what hash designers test for.

07

Timeline

Bold entries are the milestones listed in the assignment. The others give context.

  1. 1976
    Diffie–Hellman key exchange: the public-key idea.
  2. 1977
    RSA (Rivest, Shamir, Adleman): first practical public-key encryption and signature scheme, based on factoring.
  3. 1985
    Elliptic-curve cryptography proposed independently by Koblitz and Miller: same security as RSA with much smaller keys.
  4. 1997
    HMAC (RFC 2104): keyed hashing, the building block of PBKDF2 and BIP-32.
  5. 2000
    PBKDF2 (RFC 2898) and SEC 2, which publishes the parameters of secp256k1.
  6. 2001
    SHA-2 family (SHA-256, SHA-512) published by NIST, standardized in FIPS 180-2 (2002). Merkle–Damgård design.
  7. 2008
    Keccak is submitted to NIST's SHA-3 competition (opened in 2007). Bitcoin is published, and its 2009 software uses secp256k1.
  8. 2012
    Keccak wins SHA-3 (October). BIP-32 (Wuille): hierarchical deterministic wallets.
  9. 2013
    BIP-39: mnemonic code for generating deterministic keys.
  10. 2014
    BIP-44: multi-account hierarchy and coin types. Ethereum's yellow paper specifies Keccak-256 as submitted, with the original padding. The same year NIST's draft FIPS 202 adds domain-separation bits.
  11. 2015
    SHA-3 standardized (FIPS 202, August). Ethereum mainnet launches in July with Keccak-256, so "SHA3" in Ethereum code means Keccak-256.
  12. 2016
    EIP-55: mixed-case checksum addresses.

The order explains the oddities: Ethereum adopted Keccak between the competition win and the final standard, and the Bitcoin-era wallet standards (BIP-32/39/44, all using SHA-2/HMAC) were reused unchanged for Ethereum by choosing coin type 60.

256-bit variantSHA-256: 512-bit blocks, 64 roundsrate 1088 bits, capacity 512 bits, 24 rounds

Keccak-256 ≠ SHA3-256. Both use the same permutation and the same rate and capacity. Only the padding differs: FIPS 202 appends two domain-separation bits 01 before the pad10*1 rule, so the first padding byte is 0x06 instead of Keccak's 0x01. This one byte changes every digest. Try it:

Why not one algorithm for everything?

LayerWhat it must achieveChosen toolWhy another tool would not do
Key management (BIP-39/32/44)Human backup, error detection, unlimited keys from one secret, cross-wallet interoperability, watch-only xpubsWordlist encoding + SHA-256 checksum, PBKDF2 and HMAC-SHA512 derivation, a path conventionA hash alone cannot do public derivation (xpub). That needs the homomorphism of the curve: child pub = parent pub + IL·G.
Ownership (secp256k1)Anyone verifies, only the owner signsECDSA over secp256k1A hash has no key pair. RSA would need ~3072-bit keys for comparable security, against 256-bit keys on the curve.
Identifier (Keccak-256)Short, uniform, collision-resistant name for a public keyKeccak-256, truncated to 160 bitsThe public key is 64 bytes and structured (HW1: not bit-uniform). Hashing compresses it and removes the structure.
Typing safety (EIP-55)Catch typos without changing the address formatCase-based checksumA cryptographic MAC would need a key. A new format would break existing software. Case is free redundancy that old parsers ignore.

The deep reason, linking HW1 and HW2: the properties conflict. Public-key cryptography and xpub derivation need algebraic structure (a homomorphism). Addresses and checksums need the absence of structure (random-function behaviour). No single primitive can be both, so the pipeline alternates between them: structured where structure is useful, hashed where it would leak or bias.

Try it in a real wallet

Real wallets show each standard at work. Use a separate browser profile and only the public test phrase. Never put real funds on it.

  1. Install MetaMask (or Rabby or Rainbow) in the fresh profile and choose import wallet with the Hardhat phrase test test … test junk.
  2. The first account should be 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266, the same as the demo above (BIP-39 + BIP-44 path index 0). Adding accounts walks m/44'/60'/0'/0/i: i = 1 gives 0x7099…79C8, i = 2 gives 0x3C44…93BC.
  3. Import the same phrase into a second wallet app: the same addresses appear. This is BIP-39/32/44 interoperability.
  4. Switch the demo's scheme to "Ledger Live style". Account 0 coincides, but later accounts differ because the index sits at the account level m/44'/60'/i'/0/0. The same words can show different accounts in different wallets.
  5. Add a BIP-39 passphrase (offered by hardware wallets): a completely unrelated set of addresses appears, with no error message.

What to look for

  • Recovery phrase screen: 12 words from a fixed list of 2048. That is the BIP-39 encoding. Wallets reject a phrase with a bad checksum.
  • "Add account": a new BIP-32 child. Nothing new needs backing up.
  • Address display: the mixed case is EIP-55. Pasting the all-lowercase form still works. Many wallets and libraries reject a mixed-case address whose checksum does not match.
  • Signing a transaction: secp256k1 ECDSA. Once you sign, the public key can be recovered from the signature, so the address no longer hides it.
  • Export private key: the 32-byte k at the end of the derivation path. It controls one account, while the phrase controls all of them.
